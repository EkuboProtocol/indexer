## Why LaunchToken Transfer and Approval are not streamed

The log stream reads `eth_getLogs` for a static list of contract addresses
(`src/evm/logStream.ts`). Each launch token is a new CREATE2 address that is
first known from `LaunchCreated`, which the token's mint logs precede in the
same transaction, so they cannot be captured without a dynamic address set
or a per-launch receipt call. Neither is needed:

- Supply reconciles exactly without them. The token mints once, inside the
  creation, while Core brackets the payment: the first mint's amount is Core's
  debit for the position, which the indexer takes from Core's own
  `PositionUpdated` of the creation (one consistent update or the launch is
  refused), and the remainder is `requested - installed`. The tests compare
  both with the raw `Transfer` logs of the frozen receipts and of every local
  chain launch, and confirm no other transfer touches address 0.
- Holder balances and allowances are not read by the API. Market data comes
  from Core pool state and balances, which are indexed.

Indexing holders would need its own design (dynamic filters with
deployment-block catch-up) and is intentionally out of scope.

## Idempotency and reorgs

Every event row is keyed `(chain_id, event_id)` with
`event_id = compute_event_id(block_number, transaction_index, event_index)`
and inserted `ON CONFLICT DO NOTHING`; a redelivered periphery log is
recognised before its checks. All tables cascade from `blocks`, the ledger
triggers add or subtract exactly the row, owners are recomputed from the
remaining changes, and `recompute_zero_seed_launch_state` repairs a launch from
the event tables. The replay tests cover re-processing blocks, re-sending every
launch log twice, reorgs across claims, transfers and a creation, deleting in
any order, and second full replays.
