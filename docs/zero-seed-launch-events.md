# Zero-seed launch event coverage

Final interface only: EkuboProtocol/evm-contracts `853b608` (source freeze,
not deployed). ABIs: `src/evm/abis/zero-seed-launch/*.abi.json`; provenance
and hashes: `tests/fixtures/zero-seed-launch/freeze-853b608/PROVENANCE.md`.
Schema: `migrations/00140_zero_seed_launch`. No deployment is pinned
(`ZERO_SEED_LAUNCH_PINS` is empty), so none of these filters is active until a
reviewed pin exists; tests inject a local pin.

"Extension" and "periphery" are the pin's `address` and `periphery`. Every
contract filter is `address` + `topic0` (non-strict) through
`createProcessorsFromHandlers` or, for `LaunchCreated`, a dedicated processor
that also reads the raw logo bytes. The LaunchToken filters are `topic0` on
every token the extension's `LaunchCreated` names (`discoveredBy`, below). API fields are those of the API's `zero-seed-launch-api/v6` contract.

## How LaunchToken Transfer and Approval are captured

Each launch token is a new CREATE2 address first named by `LaunchCreated`
(`topics[2]`), and its mints precede that event in the creation transaction.
`launchTokenProcessors` declare `discoveredBy` (the extension, `LaunchCreated`,
topic 2), and `createEvmAdapter` (`src/evm/logStream.ts`) follows the named
addresses:

- Known tokens are loaded once when the stream starts
  (`DAO.loadDiscoveredAddresses`: `zero_seed_launch_created.token` of the
  extension) and join the address list of every range read.
- A token named inside a read range is read again, alone, from the block of
  its `LaunchCreated` to the end of the range. That captures its mints at
  lower log indexes in the creation transaction and any later log in the same
  range. Matching scans the whole batch for names before matching any log.
- The set only grows; a token of an orphaned creation emits nothing on the
  canonical chain.

Processing is in log order, so the mints are stored before `LaunchCreated`
in the same database transaction, and the creation is refused unless they are
exactly Core's installed supply and the sink remainder.

RPC cost: none without a pinned launch. With one, one address per launch in
each `eth_getLogs` (split into requests of `MAX_ADDRESSES_PER_GET_LOGS` =
1,000 addresses), one extra request per range read that creates a token,
and responses grow with token activity; the existing truncation guard
(`SUSPECT_LOG_COUNT`) still bisects a response at the cap.

Rows are raw: no balances, holders or allowances are derived and the API reads
none of them.

## Idempotency and reorgs

Every event row is keyed `(chain_id, event_id)` with
`event_id = compute_event_id(block_number, transaction_index, event_index)`
and inserted `ON CONFLICT DO NOTHING`; a redelivered periphery log is
recognised before its checks. All tables cascade from `blocks`, the ledger
triggers add or subtract exactly the row, owners are recomputed from the
remaining changes, and `recompute_zero_seed_launch_state` repairs a launch from
the event tables. The replay tests cover re-processing blocks, re-sending every
launch log twice, reorgs across claims, transfers and a creation, deleting in
any order, and second full replays; the stream adapter replay does the same for
token logs, including a restarted stream after a reorg.
